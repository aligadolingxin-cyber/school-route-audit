# 資料前處理

## 人行道

```bash
uv run pipeline/build_sidewalk.py --src <SIDEWALK_202606.zip>
uv run pipeline/build_sidewalk.py --src <...> --county 台北市
```

需要 [uv](https://docs.astral.sh/uv/)，會自動取得 Python 與 shapely。原始 zip 不納入版本庫，自 `data.gov.tw/dataset/58791` 下載後置於 `data/raw/`。

輸出至 `app/data/sidewalk/<縣市>.geojson` 與 `index.json`。這些檔案**納入版本庫**——GitHub Pages 直接自版本庫提供服務，它們即是部署產物（design D11）。

### 處理步驟與理由

**1. 去除完全重複的紀錄。** 台北市有 12 組幾何與屬性皆相同的紀錄。這是來源的資料品質問題。18,304 → 18,292。

**2. 產生識別碼。** 來源沒有 ID 欄位。語意鍵（區＋路名＋起訖＋側別）在台北市只有 7,417 個相異值對 18,304 筆——「忠孝東路七段／向陽路」一組就重複 26 次，加入路段長度後仍有 457 筆重複。故識別碼為 SHA-256 前 12 碼，輸入含語意鍵與幾何代表點（捨入至小數 6 位）。

碰撞時腳本以非零碼結束且不輸出。識別碼會被 `school-route-audit-mvp` 的評估紀錄引用，碰撞等同把評估結果掛到錯的路段上。

**3. 座標捨入至小數 6 位。** 來源存到 12 位，那是 0.1 奈米等級；而來源本身的平面精度是 2.5 公尺。6 位約 0.11 公尺，仍遠高於需要。

**4. 幾何簡化，容差 0.3 公尺。** 人行道寬度中位數僅 1.35 公尺，0.3 公尺已是其兩成，不宜再大。實測 0.5 公尺僅再省 8% 傳輸量，不值得多出的失真。簡化後若變成空幾何或非面幾何，退回原幾何。

**簡化不影響淨寬分級**——淨寬是屬性（`SWW_WTH`），原值保留，與幾何無關。

**5. 移除 `COUNTY_NA`。** 檔案已分縣市，此欄冗餘。

**6. 輸出壓平的 JSON。** 來源是 pretty-print，**61.8% 的位元組是空白字元**。

### 台北市實測

| 設定 | 原始 | gzip（實際傳輸） |
|---|---:|---:|
| 來源（pretty-print，12 位小數） | 49.96 MB | 5.53 MB |
| 壓平 | 18.32 | 5.05 |
| 壓平 + 6 位小數 | 13.57 | 2.29 |
| **壓平 + 6 位 + 簡化 0.3 m**（採用） | **8.61** | **1.48** |
| 壓平 + 6 位 + 簡化 0.5 m | 7.96 | 1.19 |
| 壓平 + 5 位小數 | 12.78 | 1.49 |

頂點數減少 58%。GitHub Pages 自動以 gzip 提供服務，故決定載入速度的是右欄。

前端實測：載入 712 ms、繪製 228 ms。

### 決定性

相同輸入重跑產出的檔案**位元組完全相同**（SHA-256 驗證）。識別碼不含亂數、時間或列舉順序。

### 更新資料時

來源為「不定期更新」。改版後重跑腳本，並**比對前後版本的識別碼集合**：代表點位於識別碼的輸入中，故幾何若調整超過 0.11 公尺，該路段的識別碼會改變。消失的識別碼代表既有評估紀錄失去對應，須另行處理（design D9）。
