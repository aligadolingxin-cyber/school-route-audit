# Design

## Context

動機見 `proposal.md` — Why。此處僅列影響技術取徑的現況與限制。

**資料現況**：三個來源皆為政府開放資料，皆非為本用途而設計，需自行前處理與接合。人行道圖資（國土管理署，含 `SWW_WTH` 淨寬）以路段為單位、分側記錄；事故資料（警政署）為點，107 年起始含經緯度；學校範圍圖（國土測繪中心）為面，但無學校類型欄位。

**資料勘查結果（2026-09-25，SIDEWALK_202606）**：

- 來源已提供**分縣市 GeoJSON 且含 WGS84 版本**，無須自行轉換座標。台北市 18,304 段，與前案顯示的數字一致。
- 幾何為 **MultiPolygon**（人行道實際鋪面範圍），非道路中心線。
- 十個屬性欄位**全數 100% 填值，無 null、無 0 值**。淨寬 0.32–15.10 公尺，中位數 1.35。
- 台北市淨寬分布：**紅（< 1.5 m）58.6%**、黃 27.1%、綠 14.3%。近六成未達法規下限。
- 檔案大小：台北市 52 MB、新北市 118 MB（WGS84 未簡化）。前案為 0.03–6.2 MB／縣市，落差一至兩個數量級。

**涵蓋落差**：人行道圖資只收錄「有人行道之處」。以路名比對大安區學校周邊 286 段 OSM 道路，**55.9% 查無人行道紀錄**，其中對不到的 99 個路名有 89 個是巷弄。

此一落差不是資料品質問題，而是本工具最重要的發現：學童實際步行的巷弄本就沒有人行道。因此設計上不將其視為「缺漏」隱藏，而視為與三個淨寬級距並列的第四種狀態。但路名比對粗糙，措辭只能是「查無紀錄」，不能斷言實地無人行道。

**部署型態**：以網址對外可存取，但不主動公開。此一型態即構成散布，觸發各資料集的出處標示義務；亦使前端金鑰暴露於公開網路。

**前案**：[Taiwan Mobility Atlas](https://yunching0513.github.io/taiwan-mobility-atlas/sidewalk.html) 已實作本 change 的多數圖層，為全國規模，技術採 Leaflet + PMTiles + Google Maps API + Supabase。其存在既是可行性證明，也界定了本專案的差異所在。

## Goals / Non-Goals

**Goals:**

- 缺漏資料在任何呈現與計算路徑上都不被當作 0。
- 任何衍生敘述都可追溯至具體資料欄位，無法追溯者不產生。
- 單一縣市的載入量與互動延遲在一般家用網路與筆電上可接受。
- 風險圖層的接入位置在 MVP 即備妥，日後接入不需改寫圖層架構。

**Non-Goals:**

- 不做障礙物圖層、共同繪圖、旅程圖與願景提案。
- 不做使用者帳號、標註或任何寫入功能；本工具唯讀。
- 不做全國一次載入或跨縣市統計。
- 不實作逐段評估；該功能屬 `school-route-audit-mvp`。

## Decisions

### D1. 資料前處理與前端分離，前端只讀已處理好的檔案

政府原始資料經離線前處理腳本轉為分縣市檔案，前端不在執行時解析原始格式、不做座標轉換、不做空間接合。前處理腳本與**其產出的分縣市檔案**皆納入版本庫；原始下載檔（ZIP／SHP／CSV）不納入。

**理由**：原始資料為 ZIP／SHP／CSV、座標為 TWD97、欄位命名不一，於瀏覽器處理將使首次載入延遲數十秒。且前處理具有可重現性價值——資料更新時重跑腳本即可，處理邏輯有跡可循。

### D2. 以 Leaflet 搭配 Canvas 繪圖；向量圖磚經實測確認不需要

採 Leaflet 搭配 GeoJSON 圖層，並啟用 `preferCanvas`。

**實測（台北市 18,292 段）**：載入 712 ms、繪製 228 ms，合計未滿一秒。互動流暢。**故不導入向量圖磚。**

**Canvas 為必要而非最佳化**：Leaflet 預設以 SVG 繪製，一個多邊形即一個 DOM 節點。一萬八千個節點會使瀏覽器癱瘓，與檔案大小無關。

**尚未驗證**：新北市資料量約為台北市的 2.3 倍（來源 118 MB 對 52 MB），為全國最大。task 14.2 應以其複測；若延遲不可接受，再回頭評估 PMTiles。

**替代方案**：一開始即採 PMTiles——效能上限較高，但引入圖磚產製流程與額外相依。實測證實不需要。

### D3. 學級以校名後綴為主、教育部名錄為佐證（實作後修正）

**原定為「以名錄接合為準，不以校名推測」。實作後改為相反的主從關係**，理由是實測：

- 名錄接合率僅 82%，且**三成以上的接合結果同名多學級**——臺北市的「大安」同時對應大安國小與大安國中，名錄無法單獨決定學級。
- 校名後綴則結構穩定：「臺北市中山區中山國民小學」的「國民小學」即是答案。

故改為：校名後綴判定學級，名錄用於佐證；兩者不一致時採名錄並記入報告。

**實測（4,336 個校地）**：名稱與名錄一致 80.6%、不一致 1.2%、僅名稱可判 10.8%、僅名錄可判 0.2%、大專分部校區 4.7%、無法判定 2.6%。

**接合的困難點**，皆已處理並記於 `pipeline/build_schools.py`：
- 校名格式在學級間不一致：國小為「南投縣中寮鄉中寮國民小學」，國中卻是「南投縣立三光國民中學」。砍掉縣市後殘留的「立」若不處理，核心名變成「立三光」，國中接合率幾乎歸零。
- 名錄用簡稱（基隆女中）而地圖用全名（基隆女子高級中學）。
- 大專的分部與校區不在名錄中，另以名稱樣式歸入大專。

### D16. 縣市由座標判定，不由校名判定

學校所屬縣市以其校地中心落在哪個縣市界內決定，縣市界取自 OpenStreetMap 的 admin_level=4。

**理由**：校名判定在國立學校上會系統性失敗——「國立仁愛高級農業職業學校」的「仁愛」是南投縣仁愛鄉，不是縣名。以校名判定時有 3.5% 無法歸屬且集中於國立學校；改以座標判定後為 0%。

**飛地必須取面積最小者**：臺北市完整位於新北市之內，嘉義市亦位於嘉義縣之內。自邊界線段組面時內孔會被填實，一個點會同時落在兩個縣市內。初版取第一個命中者，導致**臺北市整個消失、其學校全被歸入新北市**。改取面積最小的縣市才正確。

**新增相依**：OpenStreetMap 縣市界（ODbL 1.0），經 Overpass 取得並快取於 `data/raw/`。此為第二個 OSM 用途，與 D12 的道路中心線同源。

### D4. 學校地塊用冷色系，不與路段紅黃綠爭奪語意

路段著色佔用紅／黃／綠／灰的語意，學校地塊改採冷色系半透明填色加實線外框：

| 類型 | 填色 |
|---|---|
| 國小 | `#4E79A7` 鋼藍 |
| 國中 | `#76B7B2` 青 |
| 高中職 | `#B07AA1` 藕紫 |
| 大專 | `#3B5BA5` 深藍 |
| 特殊 | `#8C6BB1` 紫 |
| 其他 | `#9C9C9C` 灰 |

填色不透明度約 25%，外框為同色實線。路段為線、學校為面，視覺通道本已不同。

**理由**：若學校也用紅綠，使用者無法分辨「紅色代表這所學校危險」與「紅色代表這段路窄」。顏色在本工具中承載判讀語意，不是裝飾。

### D5. 問題摘要與改善建議採規則式產生，MVP 不使用語言模型

摘要由一組明示的規則自資料欄位產生，每條規則對應一段固定句型與其引用的欄位。

**理由**：spec 要求每句陳述可追溯至欄位，且不得產生資料中不存在的道路資訊。規則式產生**在構造上**滿足此約束——沒有虛構的可能。語言模型則需額外的事實查核層才能達到同樣保證，而那層本身也可能出錯。MVP 不需要語言模型的表達彈性。

**代價**：句子較生硬、覆蓋情境有限。若日後導入語言模型，須先建立：以規則產出的事實清單為唯一輸入、輸出逐句對回欄位、無對應者刪除。

### D6. 缺漏發生在道路層級而非欄位層級，以獨立狀態表示且不進入任何數值路徑

勘查確認人行道資料的欄位無缺漏。真正的缺漏是**整條道路不在資料集中**。因此「查無人行道紀錄」是道路的一種狀態，不是欄位的空值。分級、排序、統計與比較皆先判定該道路是否有人行道紀錄，查無者獨立計數。

**理由**：若將查無紀錄者當作淨寬 0，道路會被著成紅色、統計會被拉低，使用者將得到一張看似精確實則錯誤的地圖。而大安區學校周邊此類道路占 55.9%，誤差規模足以顛倒結論。這是本工具最可能造成實質誤導的單一風險點。

### D12. 兩層呈現：人行道多邊形與道路中心線

地圖以兩個圖層呈現道路狀況：人行道多邊形（政府資料，帶淨寬，紅黃綠著色）與道路中心線（OSM，僅用於呈現查無人行道紀錄者，灰色）。

**理由**：人行道資料集中沒有「道路」這個物件，只有人行道。若僅畫人行道，巷弄會完全消失，地圖會讓人誤以為那裡無路可走——而那正是學童步行之處。要畫出「這裡有路但沒有人行道」，必須另外取得道路網。

**代價**：新增一個資料來源與其 ODbL 授權義務，以及人行道與道路的空間對應工作。

**替代方案**：僅畫人行道——實作最省，但將最重要的發現隱藏起來，與本工具的目的相違。

### D13. 人行道與道路的對應採空間比對，不採路名字串比對

判定某條道路是否有人行道紀錄時，以幾何鄰近性比對，不以路名字串比對。

**理由**：勘查階段以路名比對得到 55.9% 查無紀錄，但路名格式不一（巷弄層級、全半形、有無「段」），字串比對會把格式差異誤判為沒有人行道。勘查用它是為了快速取得量級，實作不能沿用。

**代價**：需處理人行道多邊形與道路中心線的緩衝距離與側別對應，較字串比對複雜。緩衝距離取值列為待決。

### D14. 前處理階段簡化幾何並精簡屬性

前處理時對人行道多邊形做幾何簡化並移除前端用不到的屬性，目標為單一縣市檔案降至可於一般家用網路載入的量級。簡化容差須明示於資料說明，且 MUST NOT 大到改變淨寬分級的判讀。

**理由**：台北市 52 MB、新北市 118 MB 無法直接於瀏覽器載入。前案以 ±0.3 公尺簡化達到 0.03–6.2 MB／縣市，證實一至兩個數量級的縮減可行。

**注意**：簡化的是**幾何形狀**，不是淨寬數值。淨寬為屬性，不受簡化影響。

### D7. Google Maps 金鑰限制來源網域並設用量上限

金鑰設定 HTTP referrer 限制，僅允許部署網域；於 Google Cloud Console 設定每日請求上限與預算警示。版本庫僅含設定範本。

**理由**：金鑰於前端可見無法避免，只能限制其可用範圍。未設限制的金鑰被他人取用將直接計入使用者的計費帳號。

### D8. 出處標示常駐於介面，不置於獨立說明頁

OpenStreetMap、國土管理署、警政署、國土測繪中心的出處標示常駐於地圖區域內。

**理由**：ODbL 與政府資料開放授權條款皆要求使用時標示出處。一旦以網址對外可存取即構成散布，標示為義務。置於獨立頁面使多數使用者不會看見，不符標示之意。

### D9. 識別碼由前處理自建：語意鍵加代表點的雜湊

**來源沒有 ID 欄位**，且語意鍵不足以區辨：台北市以（區＋路名＋起訖＋側別）分組僅得 7,417 個相異值對 18,304 筆，「忠孝東路七段／向陽路」一組即重複 26 次。加入路段長度後仍有 457 筆重複。

故識別碼取 SHA-256 前 12 碼，輸入為語意鍵加上幾何代表點（捨入至小數 6 位，約 0.11 公尺）。`school-route-audit-mvp` 的評估紀錄以同一識別碼對應路段。

**實測**：加入代表點後，去重之後全縣市唯一。重跑腳本產出的檔案位元組完全相同。

**來源含重複紀錄**：台北市有 12 組幾何與屬性皆完全相同的紀錄，前處理予以去除（18,304 → 18,292）。這是資料品質問題，不是識別碼設計的缺陷。

**碰撞時讓腳本失敗**：識別碼一旦被評估紀錄引用即不得變動，碰撞會使紀錄對應到錯誤路段。腳本偵測到碰撞即以非零碼結束，不輸出檔案。

**已知限制**：代表點位於識別碼輸入中，故來源若在改版時調整幾何超過 0.11 公尺，該路段的識別碼會改變。此為唯一性與跨版本穩定性之間的取捨——在沒有來源 ID 的前提下無法兩全。資料更新時須比對前後版本的識別碼集合，處理消失與新增者。

### D17. 事故點不以紅色標行人

A1 事故點依受害者運具著色，但**刻意避開紅色**：行人為近黑、機車為磚褐、慢車為暗金、汽貨車為深藍，皆加白色外圈。

**理由**：紅色已是「淨寬 < 1.5 m」的語意。而本圖層最關鍵的判讀正是「行人死亡點是否落在紅色路段上」——若兩者同色，那個點會消失在它要控訴的路段裡。白色外圈則確保點疊在紅、黃、綠、灰任一底色上都看得見。

**一列是一個當事者，不是一場事故**：來源以當事者為列，114 年的 4,137 列實際上只有 1,607 場事故。不先合併會使點位重疊計數。受害者運具取該場事故中最脆弱的當事者（行人 > 慢車 > 機車 > 汽貨車）。

### D18. 部署時的版本號必須涵蓋相對 import

部署流程將 `index.html` 的 `__BUILD__` 置換為 commit SHA，**並改寫 `app/js/*.js` 中所有相對 import 的網址**，兩者皆未完成時讓部署失敗。

**理由**：只替換進入點不夠。`main.js` 換了網址，但它內部的 `import './config.js'` 沒換，瀏覽器仍取快取的舊版。症狀是主控台報「模組沒有匯出某個名稱」，而伺服器上的檔案其實是對的——這種錯誤極難從症狀推回原因。

這是不使用建置工具鏈的代價之一：打包器會替每個模組產生內容雜湊檔名，手寫則須自行處理相依的版本號。

### D11. 部署至 GitHub Pages，處理後的資料檔隨版本庫一同發布

以 GitHub Pages 部署。前處理產出的分縣市資料檔納入版本庫，與前端一同發布；原始下載檔不納入。Google 金鑰的 HTTP referrer 限制設為該 Pages 網域。

**理由**：GitHub Pages 為純靜態主機，直接自版本庫內容提供服務，沒有獨立的資料存放位置。處理後的資料檔即是部署產物，必須在庫內才能被取用。原始檔則體積大、格式雜、可由腳本重現，無納入必要。

**後果**：免費方案的 GitHub Pages 需要**公開版本庫**，亦即程式碼與處理後的資料皆公開可見。這與「不主動公開」並不衝突——不公開指的是不推廣、不索引，而非存取控制。若需要程式碼不可見，須改用支援私有庫的靜態主機（Vercel、Cloudflare Pages），或升級 GitHub 方案。

**資料量上限**：22 縣市各 0.03–6.2 MB 的量級下，版本庫總量在 GitHub 的一般建議範圍內。單一檔案若逼近 100 MB 須改以分割或壓縮處理。

### D15. 底圖採國土測繪中心「通用版電子地圖」，並於前端降飽和

底圖採 NLSC 的 WMTS 通用版電子地圖，免金鑰。前端以 CSS 濾鏡將其飽和度降至約 25%。

**理由**：CARTO 的 `basemaps.cartocdn.com` 現已要求金鑰，未帶金鑰的圖磚會疊上 `API KEY REQUIRED` 浮水印（前案的展示畫面亦可見此浮水印）。NLSC 免金鑰、中文地名、台灣細節完整，且與本專案其餘資料同屬政府開放資料，出處標示一致。實測 15 張圖磚零錯誤，CORS 正常。

降飽和是因為 NLSC 的道路本身以顏色分級，會與淨寬的紅／黃／綠爭奪語意（D4）。實測降至 25% 後地名、路網與學校標記仍清晰可讀，而資料層的三色明顯跳出。

**注意**：其圖磚路徑順序為 `{z}/{y}/{x}`，與多數圖磚服務相反，易誤寫。圖磚本身帶有 NLSC 的版本浮水印，屬其標示，不另行移除。

**替代方案**：CARTO 加金鑰（多一組需管理的憑證）；OSM 標準圖磚（免金鑰，但其圖磚使用政策不鼓勵長期產品化使用，且樣式同樣彩色）。

### D10. 著色依據為可插拔的設定，風險圖層依此接入

路段著色以「著色依據」為單位定義：每個依據宣告其取值欄位、級距、顏色與圖例文字。MVP 提供「淨寬」一種；風險分數日後以新增一個著色依據的方式接入。

**理由**：spec 要求風險圖層接入時不需改寫路段圖層。將著色抽象為設定而非寫死的條件判斷，即滿足此要求，且圖例可由同一份設定產生，不致與著色脫節。

## Risks / Trade-offs

**巷弄大面積查無紀錄** → 已驗證：大安區學校周邊 55.9%。處置：不視為缺漏而視為發現，以 D12 的道路中心線圖層呈現，並依 `road-segments` spec 將其占比列為主要統計數字。措辭限於「查無人行道紀錄」，不斷言實地無人行道。

**路名比對的偏誤已知但未量化** → 勘查的 55.9% 係以路名字串比對所得，可能高估。D13 要求實作改採空間比對。實作後應重新量測此比例，若與勘查值差距顯著，須更新介面上的說明文字與本文件的數字。

**與前案高度重疊** → 本 change 的圖層多數已由公開工具實現。緩解：差異化來自後續接入的逐段評估層，`road-segments` 與 `segment-detail` 已預留其位置。實作前檢視前案授權，界定可參考與不可取用的範圍。

**Google 街景服務條款與費用** → 金鑰暴露、額度超用、條款變動皆為外部風險。緩解：D7 的來源限制與用量上限；`street-view` spec 要求街景不可用時其餘功能維持可用，故服務中斷不致使工具失效。

**資料更新不定期，時效性不明** → 人行道圖資與學校範圍圖皆為「不定期更新」。緩解：於介面標示各資料集的擷取日期與資料年月，使使用者得以判斷時效。

**事故點與路段的空間關聯為近似** → 事故點座標未必精確落於對應路段上。緩解：詳細面板陳述為「該路段周邊的事故紀錄」並標明緩衝距離，不宣稱事故發生於該路段。

**校名接合失敗率未知** → D3 的接合率無法事先得知。緩解：接合報告列出未接合校名，人工補正；未接合者歸入「其他」而非猜測，不致產生錯誤分類。

## Migration Plan

**資料更新**：來源資料更新時重跑前處理腳本產出新版分縣市檔案。路段識別碼若因來源改版而變動，依 D9 的對應表處理，並檢查既有評估紀錄是否仍可對應。

**風險圖層接入**：`school-route-audit-mvp` 產出評估結果後，以新增一個著色依據（D10）與擴充 `segment-detail` 的風險分數區塊接入，不改動既有圖層。

## Open Questions

- 前處理產出採 GeoJSON 或壓縮格式，取決於單一縣市實測檔案大小。屬實作階段可決定的細節，不影響架構。
- 事故點與路段關聯的緩衝距離取值。屬參數，可於實測後調整。
- 目標人群各自對應的可及範圍參數。需查既有文獻的步行速度與可及距離設定，屬資料設定而非架構。
